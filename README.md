# RAG with Hybrid Search

A Retrieval-Augmented Generation (RAG) system built from scratch in Python,
combining BM25 keyword search and neural embedding search through
Reciprocal Rank Fusion (RRF) — with a persisted index, free local LLM
generation via Ollama, and an evaluation harness. The demo knowledge base
covers VALORANT esports: VCT tournament format, VALORANT Champions 2025
results, and profiles of top teams (NRG, Fnatic, Paper Rex) and player
transfers.

## Project structure

```
rag-hybrid-search/
├── documents/               source .txt files — the knowledge base
├── src/
│   ├── chunking.py          splits documents into overlapping word-window chunks
│   ├── sparse_retriever.py  BM25 keyword search with stopword filtering
│   ├── dense_retriever.py   neural embedding search (sentence-transformers),
│   │                        with a TF-IDF+SVD fallback for offline use
│   ├── hybrid_retriever.py  fuses sparse + dense rankings with RRF
│   ├── rag_pipeline.py      builds the LLM prompt from retrieved chunks;
│   │                        generation via Ollama (or the Anthropic API)
│   ├── build_index.py       ingestion script -> writes index.pkl
│   └── query.py             query script -> loads index.pkl, interactive Q&A
├── evaluate.py              recall@k comparison: sparse vs dense vs hybrid
├── generate_local_test.py   example: retrieval + local LLM generation
├── requirements.txt
└── index.pkl                generated by build_index.py (not committed)
```

## The pipeline

This project has two separate pipelines that run at different times.

### 1. Ingestion — `src/build_index.py` (run once, or after editing `documents/`)

```
documents/*.txt
      │
      ▼
  chunking.py        split each document into overlapping ~40-word chunks
      │               (10-word overlap, so no sentence is cleanly severed
      │                at a chunk boundary)
      ▼
  ┌───────────────┴───────────────┐
  ▼                                ▼
sparse_retriever.py          dense_retriever.py
BM25Okapi index over         sentence-transformers (all-MiniLM-L6-v2)
stopword-filtered,           encodes each chunk into a 384-dimension
lowercased word tokens       vector, normalized for cosine similarity
  │                                │
  └───────────────┬───────────────┘
                   ▼
              index.pkl
     (chunks + BM25 index + embedding matrix, saved to disk)
```

**Extract/clean step:** intentionally skipped. The source documents are
already clean plain text, so there is nothing to extract. A real system
ingesting PDFs, HTML, or Word files would add a parsing and cleaning
stage (for example with Unstructured) before chunking.

### 2. Query — `src/query.py` (run anytime after the index exists)

```
your question
      │
      ▼
  load index.pkl           no re-chunking, no re-embedding the corpus —
      │                     only the new question gets processed
      ▼
  ┌───────────────┴───────────────┐
  ▼                                ▼
BM25 search                  embed question -> cosine similarity
(exact word match)           search (meaning match)
  │                                │
  └───────────────┬───────────────┘
                   ▼
         hybrid_retriever.py
    Reciprocal Rank Fusion — merges both
    ranked lists by RANK POSITION, not raw
    score (BM25 scores and cosine similarities
    aren't on comparable scales)
                   ▼
            top-k chunks returned
                   │
                   ▼
         rag_pipeline.py (generation, optional)
    build_prompt() -> generate_with_ollama()
```

**Why two separate pipelines, not one script:** embedding a corpus is the
expensive step. Re-running it on every question would be wasteful and slow
at any real scale. Ingestion does that work once and saves the result;
query time only embeds one short string — the incoming question.

### Generation

Retrieval alone returns raw chunks. Generation turns them into an answer:

1. `build_prompt()` places the top-k chunks into a prompt template as
   context, followed by the user's question.
2. The template instructs the model to answer using only the provided
   context, to synthesize an answer from what the context describes (no
   exact matching sentence required), and to say it doesn't know if the
   context contains nothing relevant. This is what grounds the answer in
   your documents instead of the model's general training knowledge.
3. `generate_with_ollama()` sends that prompt to a local model (Llama 3.2)
   through Ollama's local API. No API key or cost.

`rag_pipeline.py` also contains `generate_with_anthropic()`, which does the
same thing through the Claude API. It requires an API key with credits and
has not been verified in this project.

Six plain-text files, each covering one topic, chunked into 28 total
passages:

| File | Covers |
|---|---|
| VCT format doc | How the VALORANT Champions Tour is structured: Kickoff, Stage 1/2, Masters, Champions; the 2026 format changes |
| Champions 2025 results | NRG's 3-2 grand final win over Fnatic in Paris, dates, prize pool, MVP |
| NRG team profile | Roster, Ethan's two Champions titles, 2026 roster changes |
| Fnatic team profile | Roster and their three 2025 runner-up finishes |
| Paper Rex team profile | Roster, Masters Toronto win, the "PRX" abbreviation |
| Notable transfers | aspas to MIBR, Demon1 to Leviatan, Derke to Team Vitality |

Run `dir documents` (Windows) or `ls documents` to see the actual
filenames; the table describes content, not exact file names.

**A lesson baked into this corpus:** esports content is full of
abbreviations (PRX, FNC, IGL, EMEA) that real users will query with.
BM25 and embeddings can only match what is actually written in the text,
so documents should spell out each abbreviation at least once.

## What's inside `index.pkl`

A single pickled Python dictionary — the project's hand-built equivalent
of a vector database:

```python
{
    "chunks": [...],              # every Chunk object: id, source doc, text
    "sparse": <SparseRetriever>,  # the full BM25 index, ready to search
    "dense_embeddings": <array>,  # shape (28, 384): one 384-number vector
                                  # per chunk
    "embedder_model_name": "all-MiniLM-L6-v2",
}
```

- **The embedding model itself is never pickled**, only its name.
  Reloading a cached sentence-transformers model is fast; repickling a
  large neural network would be wasteful. `query.py` rebuilds the embedder
  from the saved name and attaches the saved `dense_embeddings`, skipping
  re-encoding entirely.
- **It is not automatically kept in sync with `documents/`.** Editing a
  `.txt` file has no effect until `build_index.py` is rerun. Production
  RAG systems face the same issue and re-index on a schedule or on change.

`index.pkl` is a build artifact, not source data. It is excluded via
`.gitignore` and regenerated locally with `build_index.py`.

## Evaluation

`evaluate.py` measures retrieval quality instead of eyeballing it.

- You hand-write a `TEST_SET` of `(query, expected_chunk_id)` pairs
  where you already know the right answer. Include paraphrased queries
  (little word overlap with the source) and exact-term queries
  (abbreviations, names) so both retrievers get tested.
- For each retriever (sparse, dense, hybrid), it runs every query and
  checks whether the expected chunk appears in the top k results.
- The score is **recall@k**: the fraction of queries where the correct
  chunk made the top k. Run it at `k=3` and again at `k=1`. A small
  corpus makes `k=3` very forgiving, while `k=1` exposes ranking
  differences between methods.

Chunk IDs depend on your documents, so update `TEST_SET` whenever the
corpus changes. Rerun `evaluate.py` after any change to chunk size,
embeddings, or fusion to see whether it actually helped.

## Setup

```bash
pip install -r requirements.txt
```

First run of `build_index.py` or `query.py` downloads the embedding model
(~90MB) from Hugging Face. It's a one-time download, then cached locally.

For local, free LLM generation (optional):
```bash
# install Ollama from https://ollama.com, then:
ollama pull llama3.2
```

## Usage

```bash
# 1. Build the index (run once, or after editing documents/)
python src/build_index.py

# 2. Ask questions interactively (retrieval only, no LLM needed)
python src/query.py

# 3. Measure retrieval quality (sparse vs dense vs hybrid recall@k)
python evaluate.py
```

Generating a full natural-language answer (requires Ollama running):
```python
import sys; sys.path.insert(0, "src")
from query import load_index
from rag_pipeline import generate_with_ollama

hybrid = load_index("index.pkl")
results = hybrid.search("who won valorant champions 2025", top_k=3)
print(generate_with_ollama("who won valorant champions 2025", results))
```

## Key design decisions

- **RRF over weighted score fusion:** fuses on rank position, not raw
  score, since BM25 scores and cosine similarities live on incompatible
  scales.
- **Stopword filtering in BM25:** without it, filler words ("is", "for",
  "good") let BM25 give partial credit to irrelevant chunks.
- **Overlap in chunking:** each chunk shares its last 10 words with the
  next chunk's first 10, so a sentence spanning a boundary is never lost.

## Limitations

- `index.pkl` plus brute-force cosine similarity scans every chunk on
  every query. That's fine at dozens of chunks but too slow at real
  scale, where an approximate nearest-neighbor database (FAISS, Pinecone,
  Weaviate) would be used.
- The knowledge base reflects when the documents were written. Esports
  rosters and results change constantly; this is not live data.
- Small local models (Llama 3.2) can misjudge ambiguous questions even
  when the retrieved context is correct.

## Possible next steps

- Swap `index.pkl` for FAISS or a hosted vector database to test at scale
- Add a cross-encoder reranker after fusion for better top-k precision
- Expand the `evaluate.py` test set and track recall@k as the corpus grows
